# DESIGN — мульти-аккаунтный разворот (с учётом замера #8)

Дизайн уточнён по результатам бенчмарка диск-канала (server3 → Яндекс.Диск) и
скорректирован по реальной эксплуатации (см. раздел «Уточнения по эксплуатации»).

## Замер — факты

| Метрика | Значение | Вывод |
|---|---|---|
| PUT 1KB | med 739ms / p95 1320ms | запись медленная |
| GET (hit) | med 72ms | чтение быстрое (~10× быстрее записи) |
| chunk PUT→виден | med ~9s | задержка видимости файла на Диске |
| bulk WebDAV-PUT | 119 KB/s | базовая запись |
| bulk REST-upload | **436 KB/s (×3.7)** | REST сильно быстрее на запись |
| троттлинг | 429=0 до 110 req/s / conc 32 | изолированный аккаунт, короткий прогон |

**Вердикт (замер): канал латентно-связан.** Но замер шёл на изолированном
аккаунте коротким прогоном. В реальной эксплуатации аккаунт **общий** (телефон +
сервер, единый бюджет запросов), и под файловой нагрузкой Яндекс режет всплески:
ловятся 429/423, растёт задержка. То есть **под нагрузкой канал ещё и
троттл-чувствителен** — отсюда rate-лимитер и «вежливая» каденция (см. ниже).

## Решения, продиктованные замером

1. **Multi-account = ТОЛЬКО изоляция, не striping.**
   Striping по N аккаунтов ради скорости **отклонён**: 429=0 → бюджет запросов не
   исчерпан, размазывание по аккаунтам не ускорит. Multi-account остаётся ради
   изоляции (свой Диск = квота/креды/enc-ключ на юзера), не ради пропускной.

2. **REST-upload s2c — дефолт транспорта, не опция.**
   ×3.7 на запись. Go-`webdav.Transport` льёт s2c через Yandex REST при наличии
   `oauth_token`; download остаётся WebDAV GET (он и так быстрый, 72ms).

3. **Ставка на параллелизм — главный аргумент за Go.**
   Латентно-связаны → выигрыш даёт не меньше запросов, а больше параллельных
   (read-ahead прячет 72ms GET'ы, put-workers прячут 739ms PUT'ы). Горутины делают
   это дёшево; Python-треды под GIL — потолок. Go тут не «красивее», а **быстрее по
   существу**.

4. **Тюнинг-дефолты** (константы пакета `pipe`, актуальные значения в коде):
   - `ChunkDataSize` = **131071** (128KB−1) — размер данных чанка. **Жёстко привязан
     к клиенту WireTurn**: сервер обязан бить s2c ровно так же, иначе клиент не
     соберёт поток (проверено: 1MB-чанк ломал даже коннект прокси Telegram).
   - `ReadAhead` = 4, `PutWorkers` = 4 — прятать латентность параллелизмом, но
     умеренно: общий аккаунт, всплеск запросов → 429 (снижено с 16/16).
   - `PollMin` = 50ms / `PollMax` = 300ms — каденция доставки чанков (in-order).
   - `DiscoverMin` = 120ms / `DiscoverMax` = 400ms — отдельная, более щадящая
     каденция PROPFIND-дискавери готовых seq'ов (листинг дороже GET'а, аккаунт общий).
   - Бэкпрешер записи: `maxOutBuf` = 64KB (мелкий буфер — ping-фрейм не застревает
     за данными файла), `putQueueLen` = 8 (ограниченная очередь PUT → блокирует
     `Write` под завалом, RSS не убегает).

5. **Тиринг производительности.**
   WebDAV фундаментально латентный (~9s cold-чанк, КБ/с) — это **текстовый резерв**
   (мессенджер/ssh), не сёрфинг. Производительность/системный VPN = **MVP2 (olcRTC,
   real-time WebRTC)**, а не масштабирование WebDAV. Вкладываться в скорость →
   вкладываться в MVP2, не в WebDAV-striping.

## Архитектура (без изменений от каркаса)

```
Supervisor
 └─ Worker[account]             изоляция per-account
     └─ Transport.Accept()      → Session (дуплексный байт-канал)
         └─ SessionHandler.Serve(session)
```

Две оси: `Transport` (webdav / olcrtc) × `SessionHandler` (YamuxPassthrough /
VLESSBridge). Supervisor / account-изоляция / egress — общие.

## Требования к порту `webdav.Transport` (Go)

- **s2c upload — REST по умолчанию** при `oauth_token`; иначе WebDAV PUT.
- **Тюнинг-дефолты** выше (константы пакета, переопределяемы per-account позже).
- **Discovery: PROPFIND depth=1** на `tunnel/` → sid'ы (директории). depth=2
  Яндекс.Диск отдаёт **403 Forbidden** — оптимизация «sid + наличие `init` за один
  запрос» неприменима; готовность сессии проверяется отдельным GET `init`.
- **Startup-cleanup только своих stale** (по `hb` > 90s), не сносить живые чужие
  сессии (баг Python-версии, чинится в порту).
- **Rate-лимитер per-account** — token-bucket (`accountRPS`=8, `accountBurst`=8),
  общий на WebDAV-клиент и REST-аплоадер: burst поглощает пачку DC-коннектов
  Telegram, дальше сглаживает всплеск → меньше 429. Liveness (`srv-hb`) идёт
  **в обход лимитера** (`PutNoLimit`), чтобы не голодать за данными файла.
- **Bounded `http.Client`** per-account (`MaxConnsPerHost`) — не заваливать аккаунт.
- **НЕ реализовывать striping.**

## Явно отклонено (с обоснованием)

- **Striping аккаунтов ради скорости** — канал латентно-связан, а под нагрузкой
  ещё и троттлится всплесками; размазывание по аккаунтам не лечит латентность и
  требует своего multi-backend клиента (WireTurn его не умеет). Выигрыша нет.

## Уточнения по эксплуатации

Реальные прогоны (общий аккаунт, файл через туннель) уточнили дизайн:

- **Аккаунт общий, бюджет запросов единый** (телефон + сервер). Под файловой
  нагрузкой Яндекс режет всплески (429/423), растёт задержка. Это **резервный
  канал текстовой связи** (текст + мелкие фото); bulk-заливка (десятки-сотни МБ)
  насыщает аккаунт → клиент рвёт сессию. Не для файлов.
- **`ChunkDataSize` привязан к клиенту.** Оптимизировать размер чанка в одну
  сторону нельзя — 1MB s2c-чанк ломал коннект прокси Telegram. Держим 131071.
- **`ReadAhead`/`PutWorkers` снижены 16→4.** Больше параллелизма на общем аккаунте
  = больше всплеск = больше 429; выигрыша нет, вреда — да.
- **Discovery-модель, не слепой read-ahead.** Отдельная горутина PROPFIND'ит
  готовые seq'ы (щадящая каденция `DiscoverMin/Max`), reader тянет только
  обнаруженные в окне `[nextDeliver, +ReadAhead)` и отдаёт in-order.
- **Дедубль сессий.** Реап known-sid только при успешном листинге и после
  `reapMisses`=3 промахов подряд — иначе транзиентная ошибка PROPFIND сносила
  known-сессию → повторный pickup того же sid → дубль yamux-сервера на одной
  c2s/s2c-папке (воровали чанки).
- **Бэкпрешер против runaway RSS.** `Write` блокируется при `outBuf ≥ maxOutBuf`;
  очередь PUT ограничена `putQueueLen`; при `ErrTargetGone` (папка сессии удалена)
  писатель сдаётся, а не ретраит вечно. RSS под медиа ~17MB (было 118MB).

## Изоляция multi-user

- **MVP1 (webdav):** аккаунт-на-юзера (Диск = квота/креды/enc-ключ).
- **MVP2 (olcrtc):** xray UUID на одном инбаунде — масштабируется лучше.
