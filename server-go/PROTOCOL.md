# Wire-протокол (наша реализация сервера ↔ WireTurn)

Снят реверсом с клиентской стороны `webdav-tunnel`, чтобы наш сервер был
wire-совместим с WireTurn. Мы **не переиспользуем** его код — это независимая
спецификация, по которой пишем свой сервер на Python.

Обе стороны (WireTurn-клиент и наш сервер) общаются **только** через общее
WebDAV-хранилище (Яндекс.Диск). Никаких прямых соединений между ними.

## Раскладка файлов

```
tunnel/                         директория-корень туннеля (MKCOL)
  <sid>/                        sid = 8 случайных байт в hex (16 символов), создаёт клиент
    init      "ok"              клиент пишет последним — маркер готовности сессии
    hb        <unix secs>       heartbeat клиента, обновляется каждые 30 s
    srv-hb    <unix secs>       сервер пишет = «сессию подхватил»
    done      "1"               любая сторона = терминировать сессию
    c2s/                        поток клиент→сервер
      0000000001.bin            чанки, seq с 1, формат "%010d.bin"
      0000000002.bin
      ...
    s2c/                        поток сервер→клиент (та же нумерация)
      0000000001.bin
      ...
```

Направления (важно — они зеркальны):
- **Клиент** пишет в `c2s`, читает из `s2c`.
- **Сервер** пишет в `s2c`, читает из `c2s`.

## Формат чанка

Полезная нагрузка чанка до шифрования:

```
байт 0        : header  (0x00 = data, 0x01 = EOF)
байты 1..8    : uint64 BE — время создания в unix-nanoseconds (для метрик задержки)
байты 9..     : данные (для EOF-only чанка данных нет)
```

- Минимальная длина расшифрованного чанка — 9 байт. Короче — считается «ещё не
  готов», ретраим GET.
- Максимум данных в одном чанке: `ChunkDataSize` = `128*1024 - 1` = **131071** байт
  (дефолт; тюнится через URI-параметр `chunk-size`).
- EOF-чанк (`header=0x01`) закрывает поток чтения принимающей стороны.

## Шифрование (enc=1)

Если включено, содержимое **каждого** чанк-файла:

```
[12 байт случайный nonce][AES-256-GCM ciphertext][16 байт GCM tag]
```

- Ключ: `SHA256(b"webdav-tunnel-v1:" + password)` — 32 байта.
- nonce — 12 байт, случайный на каждый чанк.
- Раскладка nonce‖ct‖tag совпадает с `crypto/cipher` GCM `Seal(nonce, nonce, pt)`
  в Go и с `AESGCM.encrypt()` (которая даёт ct‖tag) в Python — wire-совместимо.

## Транспорт поверх чанков

Упорядоченный поток чанков `c2s`/`s2c` образует надёжный дуплексный байт-канал.
Поверх него работает **yamux** (мультиплексор hashicorp). Роли:

- Клиент = `yamux.Client`.
- Наш сервер = `yamux.Server`.

Конфиг клиента: keepalive включён, `ConnectionWriteTimeout=120s`,
`MaxStreamWindowSize = 24 MiB`. Наш сервер должен корректно принять апгрейд окна
и отвечать на keepalive-пинги.

### Кадр yamux (12 байт заголовка)

```
байт 0     : версия = 0
байт 1     : тип   (0=Data, 1=WindowUpdate, 2=Ping, 3=GoAway)
байты 2..3 : флаги uint16 BE (0x1=SYN, 0x2=ACK, 0x4=FIN, 0x8=RST)
байты 4..7 : streamID uint32 BE
байты 8..11: length uint32 BE
             Data → длина следующих за заголовком данных
             WindowUpdate → величина приращения окна (delta)
             Ping → опаковое значение
             GoAway → код ошибки
```

Клиент-инициированные streamID нечётные; начальное окно потока — 256 KiB,
растёт до `MaxStreamWindowSize` через WindowUpdate.

## Прикладной слой в потоке

Первое, что пишет клиент в новый yamux-поток — адрес назначения:

```
[uint16 BE host_len][host bytes][uint16 BE port]
```

Дальше — сырой двунаправленный TCP-релей между этим потоком и соединением,
которое сервер открывает к `host:port` (у нас — через upstream SOCKS5 в цепочку).

Особый случай: SOCKS5 UDP ASSOCIATE на клиенте туннелирует DNS (порт 53) как
DNS-over-TCP через отдельный yamux-поток. Для MVP сервера можно поддержать как
обычный поток к `host:53` — с точки зрения сервера это просто TCP к порту 53.

## Жизненный цикл сессии

Клиент:
1. MKCOL `tunnel`, `tunnel/<sid>`, `tunnel/<sid>/c2s`, `tunnel/<sid>/s2c`.
2. PUT `tunnel/<sid>/init` = `"ok"`.
3. Старт heartbeat (`hb` каждые 30 s) и поллинг `done`.
4. yamux.Client поверх пайпа.

Сервер (наш):
1. PROPFIND `tunnel/` depth=1 → кандидаты sid.
2. Для каждого: GET `init` == 200 → сессия готова.
3. Проверить свежесть: возраст `hb` > 90 s ⇒ stale, удалить `init` и `tunnel/<sid>`.
4. PUT `srv-hb` = unix-секунды (сигнал клиенту «подхватил»).
5. yamux.Server поверх пайпа, accept-цикл, релей потоков.
6. При завершении — PUT `done`, удалить `tunnel/<sid>`.

Тайминги (дефолты): heartbeat 30 s, stale-сессия 90 s, idle-таймаут пайпа 90 s,
poll done каждые 3 s.
