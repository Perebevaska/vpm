## 1. Контекст и модель среды

В режиме БС оператор фильтрует трафик на двух уровнях одновременно:

- **L3 (IP/CIDR).** Пакет к неразрешённой подсети дропается на 2-м хопе (ТСПУ),
  ещё до DPI. Для не-whitelist IP — 100% packet loss по всем портам.
- **L7 (SNI + TLS-фингерпринт).** Даже на разрешённом IP DPI смотрит SNI в
  ClientHello и фингерпринт. Палевный fingerprint → RST.

Практические следствия, зашитые в дизайн:

1. **Свой VPS напрямую недостижим** — его IP не в списке. Вход всегда через
   разрешённый сервис (Яндекс.Диск, видеозвонки).
2. **UDP почти весь вырезан** (QUIC, DNS, WireGuard = NO_RESP даже на whitelist
   IP). Работают TCP 80/443/22. → все транспорты поверх **TCP/TLS:443**.
3. **Нужна маскировка под браузер** — `fp=chrome`/`firefox` (uTLS) в Xray.
4. **Yandex.Cloud — главная точка обхода**: ~1 из 5 whitelist-IP принадлежит ему
   (AS200350, ~12.9k IP). Диск опирается на него.
5. **Белые списки неоднородны** по операторам/регионам. Отсюда — не один канал, а
   несколько с автопереключением.

Источник данных по спискам (обновляется еженедельно): `openlibrecommunity/twl`.

## 2. Целевая архитектура

### 2.1. Топология

```
Диск (MVP1) / olcRTC (MVP2) — WireTurn, Android:
  Телефон(БС) ─WebDAV / WebRTC→ разрешённый сервис ─→ сервер рядом с 3x-ui
        │ egress → локальный SOCKS-inbound 3x-ui → xray-цепочка → meat → выход
```

Ключевая идея: **к серверу никто не подключается входящим** — и телефон, и сервер
идут исходящими на разрешённую точку встречи (хосты Диска / SFU видео). Сервер на
проводном канале свободно достаёт и до сервиса, и до цепочки.

### 2.2. Единый seam интеграции

Серверная часть Диск/olcRTC отдаёт трафик в **локальный SOCKS-inbound 3x-ui**, а
3x-ui-роутинг заводит его в онвард-цепочку. Цепочка не знает, какой транспорт под
ней — каналы взаимозаменяемы. Клиент — **WireTurn** (Android), поднимает
WebDAV/WebRTC-туннель. Полная инструкция — `SETUP-3xui.md`, клиент —
`SETUP-wireturn-client.md`.

### 2.3. Тиры каналов (скорость/роль)

| Тир | Канал | Скорость | Роль | Статус |
|-----|-------|----------|------|--------|
| ~~1~~ | ~~olcRTC (видео)~~ | ~~до ~10 MB/s~~ | ~~скорость~~ | запаркован (§6) |
| — | ~~Functions~~ | ~~средняя~~ | — | исключён |
| 3 | Яндекс.Диск (WebDAV) | КБ/с, высокая задержка | **итоговый канал**: текст/ssh | ✅ MVP1 |

Тиры **не смешиваются в один поток** (медленный путь убьёт реордер-буфер).

### 2.4. Reverse НЕ трогаем — bypass идёт мимо

Reverse (bridge/portal) обслуживает **обратное** направление (достучаться до ollama
со стороны публичного сервера). У Диск/olcRTC направление противоположное — трафик
**приземляется** на сервер и уходит **вверх** в цепочку → **Reverse/ollama не
трогаем.** Добавляем параллельный вход (SOCKS-inbound в 3x-ui) и переиспользуем
существующий onward-outbound.

Конкретная интеграция с 3x-ui (inbound + routing + systemd + проверка) — в
`SETUP-3xui.md`.

### 2.5. Готовая база — своего кода минимум

| Задача | Решение | Статус |
|--------|---------|--------|
| Клиент Диск+olcRTC (Android) | `spkprsnts/WireTurn` — WebDAV + WebRTC + встроенный Xray, TUN, split-tunnel | как есть |
| **Сервер Диск (WebDAV-туннель)** | **наш `server-go/wtserver` (Go)** — TCP over WebDAV, yamux, AES-256-GCM, REST-аплоад, rate-лимитер. Wire-совместим с WireTurn | ✅ готов |
| Ядро olcRTC (сервер) | `openlibrecommunity/olcrtc` — 4 транспорта, upstream-SOCKS | ~~основа MVP2~~ запаркован (§6) |

Сервер Диска изначально планировался как внешний `spkprsnts/webdav-tunnel` («своего
кода не нужно»), но реализован **свой Go-сервер** — он wire-совместим с WireTurn,
мульти-аккаунтный и захарднен под реальную нагрузку (см. `server-go/`).

## 4. Отклонённые варианты

### 4.1. MVP0 — Yandex Cloud Functions (VLESS+XHTTP) — ИСКЛЮЧЁН

Идея: функция как разрешённая прокладка (mirror) форвардит HTTP на backend с
транспортом XHTTP; всегда-разрешённый домен `*.functions.yandexcloud.net`, ноль кода
на телефоне, кросс-платформенно (iOS+Android).

**Причина отказа:** на Functions **полноценный туннель не поднять** — функция живёт
≤10 мин на вызов, не держит постоянный сокет, тело ≤3.5 МБ/вызов. XHTTP это
частично обходит (дискретные пакеты), но канал остаётся request/response-огрызком:
нестабильно, дорого по вызовам (биллинг), не для интерактива. Как транспорт туннеля
не годится → исключён из плана.

Побочно потерян единственный iOS-путь (нативные XHTTP-клиенты). Возврат iOS —
открытый вопрос; kulikov0 (.ipa proxy-only) не берём.

### 4.2. iOS через kulikov0

`.ipa`, proxy-only, сомнительная дистрибуция и стабильность — не берём.

## 5. MVP1 — Яндекс.Диск (WebDAV-туннель, аварийный резерв) — ГОТОВ

**Роль.** Несгораемый резерв: КБ/с, задержка секунды, но переживает отвал
видео-канала. Для **текста/ssh/мессенджера/мелких фото**, не для сёрфинга и не для
файлов. **Android only.**

**Реализация:** свой Go-сервер `server-go/wtserver` (не внешний `webdav-tunnel`):

- **Клиент (Android):** WireTurn, режим **WebDAV** (`webdav.yandex.ru` в БС доступен).
- **Сервер:** `server-go/wtserver`, мульти-аккаунтный, нацелен на `webdav.yandex.ru`
  (+ REST-аплоад s2c через `cloud-api.yandex.net`); egress → SOCKS-inbound 3x-ui →
  цепочка. Wire-совместим с WireTurn (проверено E2E).

Принцип: трафик сериализуется в нумерованные бинарные чанк-файлы, заливается/
забирается по WebDAV поверх HTTPS (маскируется под работу с облачным диском).
yamux-мультиплекс, AES-256-GCM. Детали протокола — `server-go/PROTOCOL.md`, дизайн —
`server-go/DESIGN.md`, план/журнал — `server-go/PLAN.md`.

**Захарднен под нагрузку** (реальные прогоны телефон↔сервер): дедубль сессий,
per-account rate-лимитер, бэкпрешер записи (RSS ограничен), discovery-модель,
srv-hb в обход лимитера. Вывод эксплуатации: **резервный ТЕКСТОВЫЙ канал** — текст и
мелкие фото проходят (пинг ~1s); bulk/тяжёлое медиа (≥~10 МБ) насыщает **общий**
аккаунт Диска → клиент рвёт сессию (потолок канала, не баг сервера).

### 5.1. Куда заходить

- **Пароль приложения** для WebDAV: Яндекс ID → Безопасность → Пароли приложений
  (тип WebDAV). Опц. **OAuth-токен** — для REST-аплоада s2c (×3.7 к записи).
- WebDAV-URL: `https://webdav.yandex.ru`. Сборка/конфиг — `server-go/README.md`.
- Клиент: WireTurn (Android APK) — `SETUP-wireturn-client.md`.

### 5.2. Критерии приёмки

- [ ] `wtserver` поднят рядом с 3x-ui, egress → SOCKS-inbound → exit цепочки
      (`curl --socks5 127.0.0.1:10800 https://api.ipify.org` даёт IP цепочки).
- [ ] WireTurn (WebDAV) с телефона в БС открывает сайт / шлёт текст (медленно, КБ/с).
- [ ] Чанки чистятся, квота Диска не растёт бесконтрольно.

### 5.3. Ограничения

- КБ/с, секундные задержки — резерв; **только текст/мелкие медиа**.
- **iOS нет** (WireTurn Android-only).
- Общий аккаунт Диска троттлит под нагрузкой — не гонять тяжёлое.

## 6. MVP2 — olcRTC (WebRTC-видео) — ЗАПАРКОВАН

**Идея.** Быстрый канал (DataChannel до ~10 MB/s): данные едут через whitelisted-
видеозвонок (WebRTC SFU: WB Stream / Telemost / Jitsi). Готовое ядро —
`openlibrecommunity/olcrtc` (Go-сервер+клиент, 4 транспорта, XChaCha20+smux),
клиент — WireTurn. Своего кода почти не нужно.

**Почему запаркован (проверено 2026-07-21).** Автоматизированный, самообслуживаемый
канал через стриминги **нежизнеспособен** — платформы закрыли guest-**создание**
комнат, а логин требует аккаунта + 2FA/3FA:

- **WB Stream:** `guest-register` работает, но `POST /api-room/api/v2/room` →
  `"Guests are not allowed to create room"`. Нужен реальный WB-аккаунт.
- **Telemost:** создание только через официальный API Yandex 360 **org** (платный),
  `cloud-api.yandex.net/v1/telemost-api/conferences`.
- **Jitsi (публичный):** `meet.jit.si` → `token required`.

Guest-**join** ещё работает → канал живёт только на **вручную созданной** комнате
(1 аккаунт создаёт, сервер+клиент входят гостями; WB — vp8channel). Это не
масштабируется и требует ручного труда/аккаунта → как «скоростной авто-канал» не
годится.

**Выжившие варианты (если понадобится скорость):**
1. **Ручная долгоживущая комната** (WB/Telemost) — 1 аккаунт, разовое создание,
   авто-переиспользование, если комната не протухает. Личный, не масштаб.
2. **Self-host Jitsi на Yandex Cloud** — единственный полностью-авто путь без
   стриминг-аккаунтов: IP Yandex Cloud whitelisted (§1.4), Jitsi сам создаёт
   комнаты, datachannel. Стоит VM. Это отдельная веха, здесь не начата.

Локально механика была подтверждена: собран `openlibrecommunity/olcrtc`, сервер
вошёл в jitsi-комнату (datachannel) — работает вне БС; в БС jitsi не проходит.
Заглушка транспорта в `server-go/internal/transport/olcrtc` — не нужна (готовый
сервер её обнуляет). Деплой-референс — `SETUP-olcrtc.md`.

## 9. Сквозные требования (все MVP)

- Транспорт **только поверх TCP/TLS:443** (UDP в БС мёртв).
- VLESS-слой цепочки: **uTLS `fp`**, SNI из whitelist.
- Полезная нагрузка bypass-каналов **шифруется** (AES) независимо от TLS.
- Клиент Диск/olcRTC — **WireTurn (Android)**.

---

## 10. Риски и эксплуатация

- **Хрупкость реверс-API** (Диск, olcRTC) — держим ≥2 каналов и пул платформ.
- **Публичность убивает дыры** — не выкладываем рабочие эндпоинты.
- **Троттлинг общего аккаунта Диска** под нагрузкой — Диск только для текста/мелких
  медиа; тяжёлое → olcRTC (MVP2).
- **Неоднородность БС** — тестировать на нескольких операторах/точках.
- **iOS сейчас без канала** (Functions исключён) — учитывать при раздаче доступа.
- **ToS сервисов** — использование чужой инфраструктуры как транспорта нарушает их
  условия; осознанный выбор оператора решения.
